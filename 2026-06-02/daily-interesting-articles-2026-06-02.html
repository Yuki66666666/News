為什麼蓋房子永遠不會變便宜 / Where Are the Economies of Scale in Homebuilding?
Construction Physics · Brian Potter 2026-05-28 25 min 原文連結
為什麼值得讀 / Why it stands out

這是 2026 年上半年最值得讀的一篇工業分析長文。作者 Brian Potter 用一個極其簡潔卻有力的框架——「輸出成本 vs 原料成本的比率」（Elon Musk 稱之為「白痴指數」）——解釋了為什麼住宅建設幾十年來從未真正「規模化降本」，而且幾乎不可能。這不只是工程問題，本質上是製造業哲學問題。

摘要 / Summary

美國每年建造逾 130 萬棟新房，規模遠超大多數製造業；但即使 Lennar 年產 8 萬棟，其每棟毛利率和售價與只蓋 1,200 棟的小商幾乎相同。為什麼？Potter 引入「輸出-輸入成本比」概念：煉油廠是 1.2–1.3，BMW i3 車身各分組件平均 1.8，而傳統住宅建築已是約 2（勞工成本約占一半）。這個比率「本已很低」——等同於高度自動化工廠的效率——但它是靠人工現場拼裝達到的，而非機械化。一旦起點比率就低，規模化帶來的邊際節省空間極小：你沒有多少「傻瓜冗餘」可以消滅。

Manufactured homes（工廠預製屋）也同樣如此：Clayton Homes 41 座工廠年產 4.9 萬棟，每座工廠規模卻和只造幾百棟的小廠差不多，幾乎沒有明顯的規模效益。運輸成本（「美元密度」太低）是部分原因，但根本原因是：把木材、石膏板、混凝土轉化為房屋所需的勞動量，原本就不多。

核心觀點 / Key takeaway
住宅建築的「效率瓶頸」不在流程冗餘，而在於它早就以近乎最佳的成本結構在運作；規模化的杠杆點在原材料本身，而非裝配過程。
引發的問題 / Questions it opens

若唯一出路是壓低原材料成本或大幅減少用料，那 3D 列印建築和 CLT 木材是否真正改變了遊戲規則？AI 輔助設計能否找到「用更少料蓋同樣好的房」的路徑？

軟體的「Emacs 化」時代 / The Emacsification of Software
Quarrelsome (Thomas Ptacek) 2026-05-12 12 min 原文連結
為什麼值得讀 / Why it stands out

本文是 2026 年上半年 HN 討論度最高的「AI 改變開發者文化」論述。安全研究員 Thomas Ptacek 不談 AI 取代工程師，而是提出一個更有趣的框架：AI agent 正在把「Emacs 文化」外溢到所有軟體開發——個人化、高度客製、只為自己用的原生 GUI app，正在大規模冒出來。(276 points on HN)

摘要 / Summary

Ptacek 花 30 分鐘讓 Claude 幫他造了一個 macOS 原生 Markdown 瀏覽器，比 App Store 上所有同類軟體都好。他由此提出：AI agent 讓原生 UI 開發門檻崩塌了。歷史上 Emacs 社群靠 elisp 為自己量身打造工具，但因 UX 往往難用、醜陋，這種文化從未蔓延。現在，agent 可以生成出色的 SwiftUI 程式碼——「個人軟體」不再只限於 TUI 破爛工具，而是美觀、功能完整的原生 app。他認為這不是「Electron 消亡」的故事，而是「一切都開始 Emacs 化」：個人化、可 fork、prompt 比 source code 更重要。

核心觀點 / Key takeaway
AI 讓「為自己一個人用的好軟體」首次變得可行；分享的不是程式碼，而是 prompt 和想法。

Google IDE 演化史：從碎片化到 Cider V / A History of IDEs at Google
Laurent Le Brun's Blog · Laurent Le Brun (前 Google TL) 2026-05-09 18 min 原文連結
為什麼值得讀 / Why it stands out

這是一篇罕見的「內部視角」工程史。前 Google 工程師 Laurent Le Brun 親歷 2011–2024 年 Google 內部 IDE 的演變——從 Jeff Dean 說「不可能統一」，到最終 80% 工程師用同一個工具——提供了大型組織如何說服數萬工程師改變習慣的第一手記錄。(351 points on HN)

摘要 / Summary

2011 年時，Google 工程師可用任何 IDE，Google 也沒有統一意圖。約 2013 年，有人悄悄開始做 Cider，一個網頁 IDE，最初技術文件作者用來改 Markdown，後來加入 LSP 跨語言補全後爆炸式成長。2020 年 Le Brun 加入團隊時，決策是改用 VSCode 作為前端（Cider V）：繼承了成熟的擴充生態，省去重造前端的代價。花了兩年達到可接受狀態，2023 年底已有 80% Google 工程師主用 Cider V。統一帶來的意外回報是：公司得以在同一平台上鋪設 AI code review、Smart Paste、AI 補全等功能，槓桿極大。

核心觀點 / Key takeaway
「標準化工具」的真正價值不在工具本身，而在它創造的平台效應——有了共同基礎，每一個 AI 功能才能觸達所有人。

Windows API 正在成為 Linux 核心功能 / Linux Gaming is Faster Because Windows APIs Are Becoming Linux Kernel Features
XDA Developers · Ty Sherback 2026-05-10 10 min 原文連結
為什麼值得讀 / Why it stands out

文章清楚解釋了一個反直覺的現象：為了讓 Windows 遊戲跑在 Linux 上更順，Linux 核心正在把 Windows 原有的執行緒同步機制（NTSYNC）直接實作進去。這是「Wine/Proton 時代」進入「核心時代」的里程碑。(664 points on HN)

摘要 / Summary

2026 年 3 月，Linux 首次突破 Steam 5% 市佔（含 Steam Deck 推動）。過去改善都靠 Wine/Proton 的 userspace 工作；NTSYNC 代表新階段：Linux 核心直接原生實作了過去需要 fsync/esync 模擬的執行緒等待原語（synchronization primitives），讓 Wine 不再需要任何仿真。Valve 雖表示 fsync 已夠快，仍搭載 NTSYNC 進穩定版 SteamOS，原因是 fsync 仍是「繞道」，偶發的 deadlock 和細微行為差異難以修正；NTSYNC 從根源解決這些問題。這一模式（Windows 功能被 Linux 原生實作）不是第一次，也不會是最後一次。

核心觀點 / Key takeaway
Linux 遊戲生態的進步已從「繞道」轉向「內化」——不是讓 Linux 假裝成 Windows，而是讓 Linux 核心真正懂得如何原生處理 Windows 應用的需求。

AI 在 GDP 裡消失了：一個計量上的大問題 / Where is AI in GDP Statistics?
PIIE (Peterson Institute) · Anton Korinek, Patrick McKelvey 2026-05-18 14 min 原文連結
為什麼值得讀 / Why it stands out

這篇 Policy Brief 解釋了為何今天最重要的經濟現象（AI 高速擴張）在 GDP 統計裡幾乎是隱形的——這不是 AI 沒有實質貢獻，而是我們的統計框架根本沒有設計來捕捉這類爆炸性進步。

摘要 / Summary

Korinek 等人提出「AI GDP」衛星帳戶框架。他們估算：2024–2025 年美國 AI 生產以品質調整後的實質成長率計算，每年超過 2,000%，驅動力來自算力擴張、硬體效率提升、以及最重要的演算法進步三力疊加。名義 AI GDP 約為 2025 年的 2,500 億美元，但品質調整後的實質成長達每年 2,600%。問題是：傳統 GDP 核算沒有捕捉到「品質」的爆炸性提升，只看到花了多少錢、用了多少算力，而非能力本身提升了多少。作者呼籲統計機構儘快建立 AI 專項衛星帳戶。

核心觀點 / Key takeaway
我們或許正在漏計一場史無前例的生產力革命——不是因為革命沒發生，而是我們的尺子不對。

「壽命遺傳率 50%」其實是什麼意思？/ Heritability of Human Life Span is ~50% When Heritability is Redefined
Dynomight · dynomight 2026-02 16 min 原文連結
為什麼值得讀 / Why it stands out

Dynomight 是網路上最好的「統計批判」寫手之一。這篇文章用輕鬆有力的文字，解剖了一篇發表於 Science 的「壽命遺傳率 50%」論文，說明結論本身沒問題，但媒體報導方式（和期刊本身的標題）製造了嚴重誤解。(92 points on HN)

摘要 / Summary

傳統雙胞胎研究顯示壽命遺傳率約 23–35%。該 Science 論文建立了一個數學模型，模擬「假設沒有車禍、謀殺、藥物過量等外因死亡」的平行宇宙，在此模擬資料上計算遺傳率，得到 46–57%。Dynomight 的批評是：這不是「糾正了真實世界的偏誤」，而是「算了另一個世界的數字」。作者還發現，如果把現代外因死亡率代入模型的 x 軸，實際對應的遺傳率更接近 35–45%，遠非論文標題暗示的 50%。核心問題在 Science 一貫的「數學模糊寫法」：方法論說明支離破碎，難以重現。

核心觀點 / Key takeaway
遺傳率是一個「觀測統計量」而非柏拉圖式的真理；在「另一個世界」裡算出的數字，不能宣稱修正了「這個世界」的偏誤。
引發的問題 / Questions it opens

頂級期刊的「為一般讀者而寫」的編輯取向，是否系統性地製造了比它防止的更多誤解？Science 的文章究竟是寫給誰看的？

超越因果：數學如何橋接人文與科學之間的鴻溝 / Beyond Causality
Aeon · Gordon Gillespie 本週精選 20 min 原文連結（Aeon Essays）
為什麼值得讀 / Why it stands out

這是一篇試圖真正「解題」的哲學文章，而不只是重述 Snow 的「兩種文化」鴻溝。作者主張橋樑不是「科學普及」，而是數學——不是數學作為工具，而是數學作為一種思維語言。

摘要 / Summary

Gillespie 認為人文與科學之所以對話困難，不在於資訊落差，而在於「因果推論」的框架本身太窄：科學的「因果機制」語言和人文的「意義詮釋」語言形成本質斷裂。他主張數學——尤其是拓樸學、圖論、範疇論等結構性數學——提供了一種超越因果的關係語言，能同時描述「物理關係」與「意義關係」，不強制規定方向與機制，卻能捕捉模式與對應。這不是一個已完成的計畫，而是一個嚴肅的起點。

核心觀點 / Key takeaway
若想真正整合人文與科學，我們或許需要的不是更多跨領域對話，而是一種更根本的共同語言——而數學的結構性部分可能正是那種語言。

為什麼值得讀 / Why it stands out

今日最好的「奇文」：倫敦政府計畫花大錢挖蓄水庫來解決格林福德地鐵站的水患，結果……把一家五口海狸請來就搞定了。這是一則關於「官僚採購 vs 生態工程」的真實寓言。

摘要 / Summary

倫敦格林福德地鐵站每逢大雨就淹水。保育人士說服政府讓他們把一個廢棄高爾夫球場改造成溼地保育區，並引進一家五口海狸。海狸幾週內築壩、造池，創造出能吸收洪水的人工溼地——此前政府原本打算挖大型水庫和堤防，費用高昂。結果：水患問題基本解決，政府省下大筆工程費，地鐵站沙包也收起來了。Tyler Cowen 的評語只是：「需要政府許可才能重新安置海狸嗎？」

核心觀點 / Key takeaway
有時最有效的「工程方案」是把生態系統的自然功能還給它，成本幾乎為零。
